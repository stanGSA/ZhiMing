# P1 塔罗试点：实现与离线验收

根因整改计划（[根因整改实施计划.md](../根因整改实施计划.md)）的 P1。基线 `claude_modify_model@cadf72b`，日期 2026-10-31，按 PR #35 评审意见修订。全部离线，未调用付费模型；真实模型评测由负责人在本机执行（见文末）。

## 怎么用

`config.yaml` 中 `mode: pipeline` 时，塔罗问题走新流水线，其余问题仍走原来的 agent 循环。默认仍是 `mode: single`，流水线只在显式开启时生效。

- `pipeline.systems: [tarot]`：本阶段只开放塔罗。
- 命令行：`cli.py chat --mode pipeline`。
- 离线演示模型（`--provider demo`）只会回放工具调用、不能撰写，所以在 pipeline 模式下也继续走 agent 循环。

## 一次塔罗提问的流程

| 阶段 | 由谁完成 | 实现 |
| --- | --- | --- |
| ① 意图 | 代码 | `pipeline/intent.py`，见下方路由规则 |
| ② 资料检查 | — | 塔罗不需要出生资料 |
| ③ 计算 | 代码 | `start_reading`、`draw_tarot` 作为计划调用，经 `execute_calls` 执行：Guard、缓存、独占（每条记录只抽一次）、trace 与模型调用完全一致。用户选牌、页面所选牌阵照常生效 |
| ④ 事实表 | 代码 | `pipeline/factsheet.py`：每张牌一行，含编号、牌位、【牌名】方向、关键词、一般含义。模型只看得到 R 编号，看不到完整引用 |
| ⑤ 撰写 | 模型（1 次，不带工具） | `pipeline/compose.py`：普通文本加标记（【表态】【摘要】【分层】【引用】【建议】【收尾】），提到牌只写 `{{R2}}` |
| ⑥ 渲染与校验 | 代码 | 见下方说明 |
| ⑦ 修复 | 模型（最多 1 次） | 一次列出全部问题，并给出每个编号对应的牌位和牌（"R2=现在位【正义】逆位"），让模型重写整稿 |
| ⑧ 降级 | 代码 | 见下方说明 |

**⑥ 渲染与校验的细节：**

- `pipeline/render.py` 把占位符换成"【正义】逆位"，生成 `submit_reading` 的参数。`question_type`、`systems_used`、`evidence`、置信度、安全提示都由代码填写。
- 安全提示按"原题加本轮追问"判断，与 `validate_reading` 口径一致。风险类别和提示语在 `common/validation.py::RISKS` 中只写一份。
- `pipeline/verify.py` 在渲染后的文本上检查牌位与牌是否对应：
  - "现在位是/为/的/抽到【牌】"
  - "【牌】在/落在/出现在现在位"
  - 二选一的"A选项""选A""A位"
  
  占位符只能保证牌名和方向，牌位仍由模型书写，所以"现在位的{{R1}}"（R1 是过去位的牌）会在这里被拦下。另外还检查有没有写到未抽到的牌。
- 最后以计划调用的方式交给 `submit_reading`：`validate_reading`、存储、追问回复的保存都照旧。只有 `submit_reading` 真正保存成功才算完成；其他结局不当作完成，流程会保留下来。

**⑧ 降级的两种方式**（都由代码写，标记在 `degraded` 中）：

| 类型 | 何时使用 | 内容 |
| --- | --- | --- |
| `keywords` | 一般情况 | 按牌面关键词写一份基础解读 |
| `safety` | 高风险问题的稿子在安全规则上失败（确定性的健康、投资、生死结论，停药，劝阻就医） | 只列牌面和安全提示，不给牌面解读（计划附录 B） |

**调用上限与预算。** 每条用户消息最多 2 次模型调用，撰写、修复与可选语义审校共用这个上限；发出后失败或取消的请求也占用本轮调用名额。撰写与修复经过 agent 循环的同一个模型调用边界 `harness/loop.py::call_model`，语义审校沿用 `PolicyJudge`，三者共享当前请求的 token 预算与调用计数：

- 按本轮 token 预算准入和结算，并记录 trace；
- 预算用尽时不再调用模型，直接按 `keywords` 方式由代码降级；
- 模型没有返回用量时，不采用这份稿子，本轮以 `usage_unavailable` 结束，流程保留；
- 整轮仍受 `limits.request_timeout_s` 约束。

启用 `policy_judge.enabled` 后，语义审校会占用剩余调用名额；例如撰写后已经审校一次，则不能再发起修复或第二次审校，未通过的稿子转为代码基础解读。审校超预算或不可用的稿子不会保存为正常解读。从 agent 回退路径转入流水线时，也会换成本轮预算。

**写法记录随结果保存。** 每次保存的解读（`readings.pipeline_json`）和追问回复（`reading_responses.pipeline_json`）都会记下：调用次数、修复次数、各稿的问题、是否降级及降级方式。导出文件也包含这些记录。agent 循环写的解读，这一项为空。

其中 `model_calls` 统计同一流程已返回的模型响应，包含语义审校、超预算后丢弃、用量缺失后暂停的响应；恢复流程时累计，和本轮最多两次发起请求的上限分别计量。没有返回响应的失败或取消请求不计入此字段，可通过 trace 的错误事件及服务适配器的请求尝试记录排查。

**中断后继续。**

- 抽牌后，读解状态的快照存进 `pipeline_runs`（库版本 6），分两个检查点：
  - `computed`：牌已抽好，尚未写稿；
  - `composed`：已有一稿未通过。
- 模型出错、超时、预算或进程重启后，用户发"继续"：
  - 从 `computed` 继续，就用同一副牌重新写稿；
  - 从 `composed` 继续，就带着上一稿和它的问题直接进入修复，不再重写第一稿。
- 保存或放弃后，这一行即删除。清除记录、注销账户会一并删除；游客登录并入账户时随记录一起迁移；导出文件会列出未完成的抽牌。

**路由规则**（`pipeline/intent.py`，按顺序判断）：

1. 网页历史中选定的塔罗解读 → 追问它。
2. 不在塔罗页、且消息提到其他体系（八字、占星、姓名、解梦、运势等）→ 交回 agent 循环。
3. 本会话有抽好但没写完的牌 → 用同一副牌接着写。
4. 发"继续"或原问题，且存在未完成的流程 → 恢复该流程。
5. 消息明确指向原解读或原牌（"第二张牌""上一次的占卜""原记录""不要重新抽"）→ 追问最近一次塔罗解读。只有"什么意思""刚才"不算。
6. "请重新抽一次" → 新解读。
7. 塔罗页，或消息提到塔罗、抽牌 → 新解读。
8. 其余 → 交回 agent 循环。

## 与计划的出入

- **塔罗的意图判断全由代码完成**，不调用模型。按计划"代码优先、代码判断不了才问模型"，塔罗用不到模型，所以每轮最多 2 次调用，而不是 3 次。
- **提交沿用现有的 `submit_reading`**，没有另写存储路径。流水线产出的解读与 agent 循环的格式相同，网页和历史记录都不用改。写法记录另存一列。
- **修复让模型重写整稿，不是只重写出错的段落**（计划 P1.7 原写"只重写出错的段落"）。问题来源很多（格式、编号、牌位、校验器报错），大多无法可靠定位到某一段；整稿重写只多花输出 token，一次修复就能处理所有问题。是否改为分段重写，等真实评测的修复率和 token 数据出来再定。
- **`pipeline_runs` 只有两个检查点**（computed、composed），只保存未完成的流程，完成后即删除，库里不会多一份已保存解读的副本。
- **网页没有新增"继续"按钮。** 中断时的提示语会请用户发送"继续"。

**中断恢复的证据：**

- `test_an_interrupted_draw_survives_a_real_process_restart`：两个独立的 Python 子进程共用同一个数据库，第二个发"继续"后，牌面与第一个进程抽到的一致，且没有再抽。
- `test_an_interrupted_run_resumes_from_the_same_draw`：同一进程中新建 Runtime。
- `test_a_run_stopped_after_a_failed_draft_resumes_at_its_repair`：从 `composed` 继续时直接修复。
- 浏览器刷新的完整回归没有做，网页侧只有 `test_web_pipeline.py` 的接口测试。

**按 PR #35 评审补上的检查**（`tests/pipeline/test_review_boundaries.py`）：

- 其他体系的追问不会被当成塔罗追问；含"刚才"的新塔罗问题会重新抽牌（同会话、跨会话）。
- 高风险原题的普通追问能带上安全提示并正常提交。
- 风险识别与安全提示共用一份规则。
- 预算用尽时不再调用模型，由代码降级。
- 没有用量的回复不被采用。
- 写法记录随解读、追问回复和导出一起保存。

**合并后的预算与计数补充**（`tests/pipeline/test_model_accounting.py`、`tests/harness/test_model_call_limit.py`）：

- 可选审校与撰写使用当前请求预算，前一轮走过 agent 回退路径也不会沿用旧预算；审校超支或预算不足时改为代码基础解读。
- 撰写、修复及审校共享两次请求名额；拒绝请求时释放 token 预留，父子预算也共同约束调用次数。
- 超预算、用量缺失和审校响应均计入保存结果与导出；同会话、跨会话恢复保留计数；取消后移除计数监听，后续追问不会重复计数。

**打包。** `pyproject.toml` 的 wheel 加入了 `pipeline/`，`tests/tooling/test_packaging.py` 保证应用的每个包都在 wheel 里。另外实际构建了 wheel，装进隔离环境后在源码目录之外跑了一次脚本模型的塔罗问答，结果为 `submit_reading`，调用 1 次。

## 还需要真实模型验证的事（负责人在本机执行）

脚本模型只能证明流程与事实保证，不能证明真实回答的质量。按计划 P1 的退出标准，用 `scripts.p1_campaign` 串行执行，摘要会发布到指定目录：

```powershell
# 调参集：当前 single 与 pipeline 同批次对照（各 3 次重复、rubric v2、pro 评委），再加留出集的 pipeline 运行
.venv\Scripts\python.exe -X utf8 -m scripts.p1_campaign --campaign tarot --root reports/p1-tarot --snapshot . --baseline . --publish docs/verification/p1/tarot
# P1 结束时：最终验收集，两种模式各跑一次，期间不据此调整
.venv\Scripts\python.exe -X utf8 -m scripts.p1_campaign --campaign tarot-final --root reports/p1-tarot-final --snapshot . --baseline . --publish docs/verification/p1/tarot-final
```

`--publish` 指向的目录需要先放一份 `pricing.yaml`，可以复制 `docs/verification/p1/codego-v4/pricing.yaml`。也可以直接运行 `scripts.live_week23 --dataset … --mode single|pipeline`。

**要看的数字**（`comparison.md` 与 `failures-*.md`）：

- 提交率、脚本断言通过率
- 已提交回答的质量通过率
- 任务完成且一次做对（无工具错误、无修复、无降级）
- 修复与降级次数
- 每题模型调用（流水线每轮应 ≤ 2）
- P50/P95 耗时、每题输入 token

通过条件以最终验收集为准，见计划 P1。

## 已知限制

- **追问只指向最近一次塔罗解读**（或网页历史中选定的那一条），不支持"三天前那次"这类说法。
- **"问道"页只有消息明确只问塔罗、且不提其他体系时才走流水线。** 涉及其他体系的问题仍走 agent 循环，留到 P3。
- **`question_type` 由关键词判断。** 二选一牌阵记为 decision，含"下个月""什么时候"等记为 timing，其余记为 tarot。
- **降级解读只有牌面的一般含义或安全提示**，不结合问题。网页暂不区分正常解读与降级解读，记录已在 `pipeline_json` 中。
- **扩大高风险关键词也影响 agent 循环。** 新增"借钱、贷款、期货、理财、积蓄"等词后，agent 循环下这类问题同样要求写安全提示；离线评测的代码层高风险识别从 3/25 变为 4/25。
