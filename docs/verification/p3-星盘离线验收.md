## P3.0 留出集断言

`direct_timing_answer` 原来只认表态在“跳槽”之前的写法（“下个月适合跳槽”）。现在也认表态收住分句、出现在“跳槽”之后的写法（“下个月跳槽不太适合”）。

**仍须拒的写法**（`tests/tooling/test_heldout_timing.py`，共 20 条）：

- 同一句里表态针对别的事：“下个月跳槽前更适合先把作品集准备好”“不如换部门适合”“比留下更适合”“换城市发展更适合”；
- 表态针对的是跳槽前后的时间：“跳槽之后适合多观察团队”“跳槽以后可以慢慢适应”；
- 外层否定或回避：“很难说下个月跳槽适合”“不能说……”“不可能说……”“不是说……”；
- 不表态：“不一定适合”“未必可以”“要看情况适合与否”；
- 反问、没有表态、说的是别的时间：“下个月跳槽适合吗”“这个月跳槽适合，下个月再看”；
- 只在第二句才表态。

**接受的写法**还包括：程度词（“完全不适合”“根本不适合”）、双重否定（“不是不可以”“并非不适合”）、表态之后再转折（“不适合，但可以先投简历”）。这些都已经明确表了态。

旧口径的接受范围原样保留，包括旧口径就接受的“很难说下个月适合跳槽”。这次只放宽语序，不收紧旧口径。

**两种口径分开报告：**

- `scripts.live_test` 的检查项按新口径判定；每行另外记 `legacy_checks`、`legacy_pass`，对应旧口径。
- `scripts.heldout_rescore` 读历史批次的 live.json，用其中保存的摘要按两种口径重评，并列出摘要首句。

## 星盘流水线（`pipeline/astro.py`）

| 阶段 | 由谁完成 | 实现 |
| --- | --- | --- |
| ① 意图 | 代码 | 星盘页；或问道页里有星盘词（星盘、占星、星座、行运、上升星座、行星名……）且不提其他体系。时机还是本命也由代码判断：能读出日期范围，或有运势、时机、最近、下个月等词，就是时机；否则是本命 |
| ② 资料 | 代码 | `pipeline/requirements.py`，见下一节 |
| ③ 计算 | 代码 | `start_reading` → `compute_natal_chart` →（时机题）`compute_transits`，都是计划调用，经 Guard 执行 |
| ④ 事实表 | 代码 | 本命：行星落座、宫位（出生时间已知时）、按容许度最紧的 8 个本命相位。时机：慢行星优先的行运相位，最多 12 个，与 `AstroPlugin.project` 给 agent 的那 12 个相同；再加被这些相位触及的本命行星落座 |
| ⑤ 撰写 | 模型（1 次，不带工具） | `compose.ASTRO_SYSTEM`：星座、宫位、相位、日期只写编号；精确日期是计算时刻，不是事件日期；问职业时回答做事方式；出生时间未知时不提宫位和四轴 |
| ⑥ 校验 | 代码 | 闭集检查（见下）加共用的措辞规则，然后照常经过 `validate_reading` |
| ⑦ 修复 | 模型（最多 1 次） | 与 P2 相同，修复请求引出触发句 |
| ⑧ 降级 | 代码 | `keywords`：按行运相位、本命落座、宫位、相位分层，列出各项和关键词；`safety`：只列依据和安全提示 |

**渲染出的文字：**

- “本命太阳在金牛座”“本命太阳在第11宫”“本命太阳与月亮四分相”；
- “行运土星与本命太阳三分相（2026年11月14日精确，北京时间）”；不是北京时间时，括号里写“America/Los_Angeles当地日期”。

**闭集**（`Astro.problems`）：正文里手写的下列内容必须与本次计算一致，否则在提交前报出，进入一次修复：

- 本命行星的星座、宫位；
- 上升、天顶的星座；
- 相位：只认本命相位和本次行运相位；
- 日期：和某个行运相位写在同一句的，必须是这个相位自己的精确日期；单独写的，只认事实表列出的行运日期、日期范围的首尾两天和出生日期。只核对“任一行运的日期”太宽：两个月里几乎每天都有某个相位精确，第一次全量测试正是这样放过了一个错日期。

另外三种情况一律拒绝：

- 写行运星的星座或宫位；
- 出生时间未知时写宫位、上升或天顶；
- 写不存在的日期（如“11月31日”）。

**还交给 agent 循环的**（记入回退比例。其中“文字给出生资料”在主集里很常见，P3 跑主集 60 题之前必须由代码接手，计划在八字 PR 里与八字一起做）：

- 对已保存解读的追问；
- 更正出生资料；
- 在消息里用文字给出生资料，而出生表单没有资料（解析地名要用地点工具）；
- 合盘、推运、返照、小行星等计算器没有的技法；
- 同时提到其他体系的问题（P3.5）。

## 资料检查与追问（`pipeline/requirements.py`，P3.1）

`REQUIREMENTS` 把 §3.5 星盘两行写成数据，并注明每一项由谁执行。

| 情形 | 处理 |
| --- | --- |
| 出生表单或画像缺日期、时区或地点 | 按模板请用户补出生信息表，本轮结束，流程存为 `awaiting_input`。用户补好表单再发消息，就从②继续；还是没有资料就交给 agent 循环 |
| 时机题读不出日期范围（“最近”“这段时间”） | 模板追问“想看哪一段时间？……”，用户的回答由代码读出范围后继续 |
| 范围超过 3660 天 | 追问，请缩小范围 |
| 计算器抛出 NeedsInput（出生时间、新疆钟表时区等） | 原样转成追问，用户回答后由计算器自己的取证函数读取 |
| 追问两次仍没有结果 | 第三条消息交给 agent 循环 |

追问的回答必须是本轮对话里紧接着这个问题的一条消息：

- 另一个对话里遗留的追问不会被当成回答；
- 中间问过别的事，原来的追问也会作废；
- 结束后的流程从 `pipeline_runs` 删除。

日期范围由代码读出（`asked_range`），优先使用 Guard 自己的 `question_range`。另外还认：

- 指定日期区间，后一个日期可以省略年月；
- 今年、明年、上下半年、某年；
- 某月：早于当前月份的算明年；
- 这周、下周、下周三；今天、明天、后天；
- 接下来 / 未来 N 个月或 N 周。

“最近”“这段时间”之类不猜范围，一律追问。

### 时机题的咨询时区（负责人 2026-11-07 的口径）

`period_choice` 按顺序取：

1. 用户在本问题里说明的时区或城市（“按北京时间”“按出生地当地时间”，沿用 `confirmed_timezone`）；
2. 画像里保存的咨询时区；
3. 出生在北京时间的，用北京时间；
4. 说了现居地或时区、但代码解析不出来的，追问；
5. **海外出生、没有说明现居地的，用出生地时区**，代码在收尾里加一句：“日期按出生地洛杉矶的时区（America/Los_Angeles）计算；如果你现在住在别处，告诉我所在城市，可以按当地时间重新计算。”；
6. 其余（新疆时间、写作 UTC+8 的钟表）照旧追问。

“海外”沿用八字和 `plugins/direct.py` 的口径：出生钟表时区不是 `Asia/Shanghai`、`Asia/Urumqi`、`Etc/GMT-8`。

这条口径只在流水线里生效，`plugins.context.period_timezone` 和 single 模式都不变。

默认时区由流水线写进 `state["timeframe_tz"]`，`compute_transits` 不另传 `tz`，它自己的检查原样执行。

**仍须追问的说法**（`tests/pipeline/test_astro_requirements.py`，共 14 条）：

- 现居地：“我现在住在多伦多”“我人一直在国外”（中间插了程度词）“常年在海外工作”“定居温哥华”“搬到了悉尼”；
- 否定：“我不在国外”“已经不住洛杉矶了”“不是住在洛杉矶”；
- 双重否定：“不是不在国外”；
- 转折后另说现居地：“出生在洛杉矶，但现在人在上海工作”；
- “我在国内”“已经回国了”；
- 用文字说了时区但解析不出来：“按多伦多时间”“用UTC”。

网页附在消息后的“我在出生信息表中填写的资料……出生地点……”是出生地，不算现居地。
