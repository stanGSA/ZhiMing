# 第 6 项：功能隔离与出生资料一致性验收

验收日期：2026-10-27；提交整理日期：2026-10-28。实施基线：`ecfc748`，本报告随第 6 项修复一同提交。

## 范围

保留已有的各功能独立运行时、排盘、对话、锁和进度队列，补齐共享出生资料变化后的结果一致性。服务重启身份恢复、多设备同步与持久任务恢复仍属于第 11 项。

本次修复三个已复现场景：重新排盘后仍展示旧生辰解读；旧标签页覆盖较新的共享生辰；其他功能改档后，运行中的旧任务仍正常提交。

## 实现

1. 共享出生资料增加单调递增的 `birth_version`，与用户画像版本分开。时间格式和未知时辰等输入先规范化；相同资料不增加版本、不清空其他排盘。清除记录后仍增加版本，防止旧标签页重新写回已删除资料。
2. 保存资料、直接排盘和聊天使用同一更新逻辑与用户级短临界区，统一更新画像并处理失效。数据库写入失败不会先推进内存版本。模型调用期间不持有资料锁。
3. 生辰变化会清理依赖旧资料的当前解读、计算、缓存及模型上下文，旧页面对话标记为旧生辰记录。历史记录保留原计算与出生资料快照。综合咨询未完成的独立塔罗牌面及其引用保留。
4. 八字、星盘、每日运势及综合咨询登记生辰依赖任务；任务期间拒绝改档，相同资料仍允许跨功能使用。正常结束、异常及取消都会释放登记。综合功能保守地视为可能依赖生辰；专用塔罗页不登记生辰依赖。
5. 解读提交前检查版本，在异步策略检查、审校后，持久化写入前再次检查。显式历史追问使用历史快照，不改写共享生辰，不重新排盘或抽牌。
6. 前端接收资料版本与功能会话修订号，避免旧响应回写。标签页通过 BroadcastChannel 通知版本变化，重新聚焦时也刷新。有草稿时保留修改并显示两个明确选择；无草稿时同步表单和折叠摘要。后台刷新保留正在查看的历史解读。运势页在生辰版本变化后重新计算流日十神，丢弃旧请求的晚到响应。

## 接口约定

- `GET /api/session?system=...` 返回 `birth_version`、`session_epoch`、`session_revision`、`birth_stale`。
- `POST /api/chat`、`POST /api/chart` 可在 JSON 中携带非负整数 `expected_birth_version`，或通过 `X-Zhiming-Birth-Version` 请求头传递。
- `PUT /api/birth` 保持原始出生资料 JSON 结构，通过 `X-Zhiming-Birth-Version` 请求头传递预期版本。
- 不携带版本的首次资料写入和不改变资料的请求保持兼容；已建立版本后的资料变更必须携带正确版本。显式提供的过期版本即使资料相同也会被拒绝。
- 冲突返回 HTTP 409，`detail` 为含 `code`、`message` 的对象。代码分别为 `birth_version_conflict`、`birth_version_required`、`birth_in_use`。
- 排盘、保存生辰接口返回完整功能状态，失败需补充输入及安全暂停分支亦返回相应状态，便于同时移除旧解读。
- 历史记录返回 `birth_context`、`historical`、`stale`；资料变化后可识别为旧资料解读。

## 数据迁移与边界

SQLite schema 升级至版本 5，为 `readings` 增加 `birth_context_json`，默认 `{}`。新增浏览器生辰相关解读保存版本与表单快照。旧记录没有该快照时保持为空，不能伪造历史依据；原有计算快照仍保留。CLI/MCP 的原有计算入口不要求浏览器版本。

共享生辰版本和活动任务登记仍属于单进程内存状态；出生资料快照随解读持久保存，并不代表已经实现重启后的身份或任务恢复。
