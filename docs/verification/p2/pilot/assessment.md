### 3.2 失败出在哪里

pipeline 唯一的质量失败是 `dream_late_grandmother` 第 3 次。这一条两稿都没通过提交前检查（每稿 1 个问题），由代码按 `keywords` 降级。降级正文对每个意象只写“梦见「房子」。这个意象常和房子、场所有关。”，关键词等于没说内容，评委判 `supported_conclusion` 失败。

**所以要解决的是修复率太高（12/18），以及降级正文太空。** 修复和降级按题分布如下：

| 题 | 修复 | 降级 |
| --- | ---: | ---: |
| 去世的奶奶 | 3/3 | 2 |
| 被追进考场（同一个梦） | 3/3 | 1 |
| 家里进水和蛇 | 2/3 | 1 |
| 掉牙 | 2/3 | 0 |
| 商场迷路 | 1/3 | 0 |
| 生病住院（高风险） | 1/3 | 0 |

**摘要和旧 trace 没有展示修复原因，但数据库已保存问题全文。** 摘要只保留每稿问题的条数，旧 trace 的 `repair` 阶段也只有 `problems=len(problems)`。基线代码的 `PipelineRun.record()` 则保留完整的 `problems` 列表，并在提交时写入 `readings.pipeline_json`。只要原批次的 workspace 数据库仍在，就能按 `reading_id` 取回各稿的问题；不能据摘要和 trace 推断负责人本机无从查询。本次增加 trace 事件，方便后续直接汇总（第 5 节）。

原批次数据库位于对应运行目录下的 `workspace/data/app.db`（以该目录的 `config.yaml` 中 `paths.app_db` 为准）。在本机只读打开后，可查询：

```sql
SELECT reading_id, json_extract(pipeline_json, '$.problems') AS problems
FROM readings
WHERE json_array_length(json_extract(pipeline_json, '$.problems')) > 0;
```

问题全文可能包含姓名和梦境片段，应留在本机。上述字段保存问题文字，不等于保存了所有失败稿全文。本次复核没有读取原批次数据库，下面的归因仍是待核实的推断；重跑前应先检查历史实际原因。

### 3.3 离线复现（推断，未用本批原稿验证）

我在当前代码上，用调参集的原题跑抽取和词典查询，再把常见写法逐句送进提交前检查（`Dream.problems`）。下列写法会被拒，**按句意都不应拒**：

| 原题 | 被拒的写法 | 被拒原因 |
| --- | --- | --- |
| 去世的奶奶 | 梦里**奶奶**为你做饭，象征着被照顾的感觉 | “奶奶”在词典里是另一个意象“祖父母”。这次命中的是“去世的亲人”，原话是“去世的奶奶”，所以被判为解读了没命中的意象 |
| 去世的奶奶 | 奶奶在老房子里给你做饭，这个画面往往反映…… | 去掉命中意象后，剩下的“**里给**”与原话共享两个字，被当成梦里的其他内容 |
| 被追进考场 | **同一个梦**反复出现，往往提示这份压力还在 | 用户原话有“同一个梦”，被当成梦里的内容 |
| 被追进考场 | 你梦里被人追着一直跑，**这个梦**说明…… | 前一分句复述了细节，后一分句以“这个梦”作主语，也被当成解读那个细节。撰写提示词明确允许“这个梦”作主语 |
| 生病住院 | 这个梦不是**健康**的预兆，更多反映你最近很累 | “健康”出自用户的提问（“是不是预示我的健康要出问题”），不是梦里的内容 |
| 商场迷路 | 「手机」**没电**，往往和沟通受阻有关 | “手机”的词典含义本身就写了“没电或损坏”，仍被判为事实表之外的内容 |

这几种写法都落在“只能解读事实表里的意象”这条检查（`Dream.unlisted`，PR #40 评审 1）或词典别名检查上。“去世的奶奶”一题 3/3 修复、2 次降级，与第一行和第二行一致。但本次尚未读取本批数据库中的实际问题文字，也未用原稿验证，这个归因仍是推断。

另外两类被拒**属于设计如此**，本次不改：

- 写到未收录的意象（“考场”“住院”“找不到出口”“家里进水”）：只要提到就拒，不论是不是在解读。
- 用事实表之外的细节作解读主语（“巨大的商场往往代表……”“蛇在水里游来游去，往往和……有关”）。

本次只在撰写提示词里讲清楚怎么写：先复述细节，再另起一句，用编号或“这个梦”作主语解读。

single 的工具错误里，同样有“‘祖父母’不是本次命中的意象”4 次、“意象‘同一个梦’未命中”4 次，说明 single 也会这样写。

## 5. 调参：本次 PR 改了什么

**主要改解梦，另有两项全体系共用的改动（第 5、6 条）；姓名、每日运势的提交前检查和提示词不变。**

1. **只能解读事实表里的意象（`Dream.unlisted`）**：放宽第 3.3 节的四种误拒，评审 1 要求拦下的写法照样拒。
   - 用户原话里以“是不是、要不要、什么意思、帮我解梦……”开头、且不含“梦见、梦到、梦里、梦中”的明确提问不算梦里的内容；疑问语气须有问号，或明确以解梦请求、“这个梦”等开头。叙述里的疑问（“有人问我能不能打开地铁闸机”）、引号内的对话，以及“有人问我：”紧接的分句仍保留；“能不能打开地铁闸机我记不清了”这类陈述也保留。“梦见地铁闸机是什么意思”含“梦见”，仍算梦里的内容。
   - 事实表本身写到的内容（命中意象的关键词和一般含义）不算“不在事实表里”。
   - 主语是整个梦（这个梦、同一个梦、这类梦……）时，不因前一分句复述了细节而拒。但如果主语自己带着别的内容（“这个梦里的考场象征……”），照样拒。
   - 移除命中意象和通用词后，单独剩下的“里、给、把、让、为、着”连接片段按虚词处理；不从完整汉字词内部删除单字，“门把手”“着装”仍须检查。
2. **用户原话的结尾别名（`plugins.dream.validation.phrase_aliases`）**：命中意象的原话以另一个别名结尾时，比如“去世的奶奶”里的“奶奶”，将这个确切词映射回本次命中的“去世的亲人”，不额外授权“祖父母”的其他同义词（如“爷爷”）。流水线前置检查和最终插件校验共用这条映射；最终校验仅在本次 `pipeline_run` 提交期间启用，single 和后续 agent 回合保持原规则。“去世”（死亡）仍是另一个意象。
3. **撰写和抽取的提示词（`pipeline/compose.py`）**：
   - 撰写：可以复述梦里的细节，但复述之后另起一句，用编号或“这个梦”作主语解读，不用“这个画面、这种场景、这说明”去承接事实表没有的内容；未收录的词复述时也不要写。
   - 抽取：程度、持续、否定或结果（“一直跑、不敢下去、没电了、什么都没复习”）不单独成项；修饰某个人或物时，归入那个人或物（“手机也没电了”→手机）。这样它们不再成为“未收录”的禁用词。动作意象（被追、掉牙、迷路）照常抽。
4. **`keywords` 降级的正文**：每个意象改写词典一般含义的第一句（“「掉牙」：梦见掉牙，常与担心失去掌控、形象受损或表达受阻有关。”），不再只列关键词。这句话也要先通过本篇的提交前检查，不通过就退回原来的关键词句。**什么时候降级、降成哪种，都没有改。** 这一条如果负责人认为算“改降级规则”，可以单独撤掉，不影响前三条。
5. **记录各失败稿的问题文字（`pipeline/runner.py`，全体系）**：trace 增加 `problems` 阶段，带上问题的文字；数据库原有的 `pipeline_json.problems` 继续保留。新增 `scripts/pipeline_problems.py`，在本机读出每条回答各稿的问题；`--tally` 仅输出固定类别标签和计数，未知错误归为“其他校验问题”，不输出经正则替换后的原始错误，避免姓名等未加引号的原文泄漏。发布的摘要格式不变。
6. **修复请求去掉塔罗措辞（`pipeline/compose.py`、`runner.py`，全体系）**：共用的 `repair_messages` 原来对所有体系都写“R1=去世的亲人位「去世的亲人」……写某个牌位时，只能用该牌位对应的编号”。解梦 12 次修复收到的都是这种措辞，姓名和每日运势各 1 次也一样。现在只有塔罗保留牌位说法，其他体系改为“可引用的编号只有：R1=「掉牙」；R2=「被追」。”。
