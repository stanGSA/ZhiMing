## 3. 修复、降级与质量失败的归因

逐条见负责人发布的 [repair-attribution.md](repair-attribution.md)；下面是我对照 pipeline-problems-raw、repair-quotes 和原稿后的复核结论。14 次修复的 30 条实际引句都能在被拒稿里找到，都没有原样留在最终回答里。

### 3.1 解梦：5 次修复，2 次降级

| 题号 | 触发写法 | 归因 | 后果 |
| --- | --- | --- | --- |
| falling_from_height#1 | “你描述一下子就惊醒” | 用户原话“一下子就惊醒了”的复述被当作事实表外内容。属于 r13 §4 的“解梦表达受限” | 修复一次通过 |
| falling_from_height#3 | “立刻惊醒” | 同上 | 修复一次通过 |
| dinner_with_ex#1 | “醒来一整天心情都不好”“气氛却让人不自在” | 同上：用户原话里的醒后情绪和饭桌气氛 | 修复一次通过 |
| dinner_with_ex#2 | 首稿“梦里气氛让你不舒服”“醒后一整天心情不好”；修复稿“这个梦让你醒来心情不好” | 同上。修复稿换了说法，“不好”又被拦下 | **keywords 降级**，质量通过 |
| dinner_with_ex#3 | 首稿“情绪也延续了一整天”；修复稿“这顿饭的气氛让你不舒服” | 同上 | **keywords 降级**，质量通过 |

这些都来自 `pipeline/dream.py` 的 `unlisted`。它会检查解读动词（说明、反映……）前的主语，以及逗号前延续到下一分句的话题；去除命中意象、通用词和已识别的情绪表达后，剩余内容若与用户原话共享两个字的片段，就可能被当作事实表外内容拒绝。

不能据此概括为“用户自述的情绪不能作为解读主语”。代码已有 `FEELING_REFERENCE`，注释明确允许独立讨论感受；`other()` 也会先去除这些情绪词。用冻结代码的 `unlisted` 做最小离线对照，在用户原话同时包含“醒来心情不好，很难过”的条件下：

| 写法 | 结果 |
| --- | --- |
| “醒来心情不好，说明你需要留意情绪。” | 拒绝，剩余的“不好”被当作事实表外内容 |
| “醒来难过，说明你需要留意情绪。” | 通过 |
| “这种情绪说明你需要留意休息。” | 通过 |

- 不是编造：本轮触发的内容都在用户原话里。
- **情绪表达覆盖不足。** “心情不好”等写法未被现有情绪识别完整覆盖，属于已有允许范围内的覆盖问题，不能一概认定为有意禁止。修复须验证用户自述、话题延续及仍须拒绝的未收录意象，不能直接放过所有情绪前缀或剩余词。
- **场景范围另行判断。** 饭桌气氛等未收录场景是否可以参与解读，涉及允许范围，扩展前需由负责人决定；不能与情绪词覆盖遗漏混作同一项规则变更。
- 上述最小对照只核对现有校验行为，没有修改冻结代码或重跑模型。本次只修正文档归因，已发生的修复、降级及评分保持原记录。

### 3.2 姓名：7 次修复，2 次降级

- **首稿的 18 条问题**：17 条是 r13 新加的 `repeated_label` 拦下的姓名或格名重复（“天格天格31”“诸葛明月的人格人格23”），1 条是三才归属。都是真实的写法问题，不是误拒。
- **两次降级是代码误拒。** 修复稿分别写了：
  - `compare#2`：“刘阳的外格2与刘洋的外格一样属传统‘凶’数”
  - `compare#3`：“刘阳的外格2与刘洋的外格一样是2数”

  `plugins/name/validation.py` 的 `GRID` 把“外格一样”里的“一”读成外格的数值 1，再与计算的外格 2 比对，报“刘洋的外格1与本次计算不符”。离线用冻结代码复现：

  ```python
  >>> [(m.group(0), number(m.group(2))) for m in GRID.finditer("刘阳的外格2与刘洋的外格一样是2数")]
  [('外格2', 2), ('外格一', 1)]
  ```

  两名的外格都是 2，两句话都写对了。属于可定位、造成降级的误拒；两条降级回答质量都通过。

- 另有 5 条已提交回答保留了“三才配置三才配置”一类重复，与 r13 §4 的“三才标签重复”相同，不在 `repeated_label` 覆盖范围内。

### 3.3 每日运势：2 次修复，无降级

- `health_risk#1/#2` 首稿被报“不能给出停药建议”。触发句是“不自行停药观察”“不自行停药或改量”，两句都在劝阻自行停药，属于否定写法的误拒。
- 修复一次就通过，没有降级，两条质量都通过。
- `common/output_policy.py` 的 `medication_error` 已明确要求拒绝肯定式用药指令、保留否定表达和医生转介。冻结代码会拒绝“不自行停药或改量”，却允许“不要自行停药或改量”“不能自行停药”，同时仍拒绝“建议自行停药”。原因是 `MEDICATION_NEGATION` 未覆盖“不＋自行”的写法，属于**现有否定语义的识别遗漏**，不能仅因它位于共用安全代码就认定修复需要改变规则语义。
- 后续修复应配齐肯定式停药建议、双重否定、引述与医生转介等守卫。若另外扩大允许的用药建议范围，才需单独确认规则变更。本次不改代码，列入已知局限。

### 3.4 流水线的质量失败：2 条，都在每日运势

`daily_final_overall#2/#3`，只有 `time_consistent=false`，没有修复和降级。

- 当天流日乙酉因节气换月分成两段（当地 00:00–17:52:05、17:52:05–23:00），23:00 起是丙戌。时段都由代码渲染，与计算一致（[review-fact-excerpts.json](review-fact-excerpts.json)）。
- `#2`：评委理由里写了“time_consistent应判true，我先前若判false需修正”，布尔值却是 false，理由和结论互相矛盾。
- `#3`：评委承认丙戌段换算正确，其换算质疑不足以说明时间错误。但原始回答只展示了第一段乙酉的“仅00:00–17:52”，随后转到23:00后的丙戌，没有展示17:52:05–23:00的第二段乙酉。分段事实本身正确，不等于“仅”的排他表达及整日覆盖没有歧义；这条应记为**评分存在争议、分段标签表达待核查**，不能直接认定为纯粹评委误读或排除渲染问题。
- 两条都保留原判，不改分。`#2` 有明确的理由与布尔值矛盾；`#3` 需分别检查评委理由、事实标签及最终回答覆盖范围。现有证据不足以把两条一并归为“不是代码缺陷”，但不影响按原分计算的10/12及四项验收结论。
