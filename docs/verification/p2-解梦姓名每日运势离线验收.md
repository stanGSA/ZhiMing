## 流水线的通用部分（PR #40）

P1 的 runner 只服务塔罗。本 PR 把它拆成通用流程和按体系的部分：

- `pipeline/runner.py` 只保留各体系共用的步骤：存流程、一次撰写、一次修复、渲染、提交、降级。
- `pipeline/system.py` 定义每个体系要提供的部分：
  - 哪些消息归它（`detect`）；
  - 计划调用（`compute`）；
  - 事实表（`facts`）和撰写请求（`messages`）；
  - 提交前的闭集检查（`problems`）；
  - 由代码补进解读的内容（`complete`）；
  - 由代码写整篇的情形（`template`），以及降级解读（`degraded`）。
- 塔罗的这些部分原样移到 `pipeline/tarot.py`，行为不变。P1 的 64 项流水线测试全部通过，只改了一行断言：配置里启用的体系现在是 `("tarot", "dream")`。唯一的实际改动在“代码写的解读也提交失败”这条极少见的路径上：
  - P1 时，这种失败会冒到最外层，记成 `model_error`；
  - 现在返回提交工具本身的结局，并保留流程，用户发“继续”即可接着写。
- 体系按顺序判断：塔罗、解梦。一条消息归第一个认领它的体系；都不认领就交回 agent 循环。
- `Runtime.plugins` 按体系名提供计算插件，供流水线直接使用（例如解梦的词典匹配器）。
- `config.yaml` 的 `pipeline.systems` 改为 `[tarot, dream]`。仍只在 `mode: pipeline` 时生效，默认模式仍是 `single`。

## P2.1 解梦（PR #40）

| 阶段 | 由谁完成 | 实现（`pipeline/dream.py`） |
| --- | --- | --- |
| ① 意图 | 代码 | 解梦页；或问道页里有“梦见、梦到、做梦、噩梦、解梦……”且不提其他体系。以下情形 P2 仍交回 agent 循环：网页历史中选定了记录；消息回指旧解读（“刚才那个梦”“那段解读”“你说的”）；已有解梦记录、而这条消息没有叙述新的梦（没有“梦见、梦到、做了……梦”） |
| ① 抽取意象 | 代码加 1 次模型 | 见下方说明 |
| ③ 计算 | 代码 | `start_reading`、`lookup_dream_symbols` 作为计划调用，经 Guard 执行 |
| ④ 事实表 | 代码 | 每个命中意象一行：编号、「意象」、用户原话、关键词、一般含义；另列一行“未收录（不要提及，程序会另外说明）” |
| ⑤ 撰写 | 模型（1 次，不带工具） | `compose.DREAM_SYSTEM`：意象只写 `{{R2}}`，渲染为“「掉牙」”；含义只从事实表出发；只谈心理与情绪，不谈预兆；共用 `SCENARIO_RULE`；去世亲人、医院等语气温和 |
| ⑥ 校验 | 代码 | 见下方说明 |
| ⑦ 修复 | 模型（最多 1 次） | 与塔罗相同 |
| ⑧ 降级 | 代码 | `keywords`：每个命中意象及其关键词，意象多时几个合成一层，连同未收录说明最多 6 层，不丢意象；`safety`：只列命中意象和安全提示 |

**抽取意象**（计划 §3.4“模型补全”，按负责人决定“代码优先，必要时调一次模型”）：

1. 代码先找出原话里的词典意象：别名的最长匹配，加上 `NORMALISATIONS` 的固定句式（“牙齿一颗一颗掉下来”→掉牙，“被一条大狗追”→被追）。
2. 再调一次模型（`purpose=intent`，不带工具，只返回 JSON）。模型会看到代码找到的词，但要按原文取舍：这些词可能不属于梦境，比如“最近工作压力大”里的词。
3. 代码只保留：
   - 逐字出现在原话里的片段；
   - 能由片段规范化得到的意象，口径是 `DreamMatcher.supported`，与工具自己的校验相同；不满足时退回用户原话（不超过 12 字）。
4. 模型的回复不可用时（不是 JSON、被截断、预算用尽），或回复的条目全部无效时，改用代码找到的词。只有模型明确回复空列表，才当作原话里没有梦境。trace 的 `extract` 阶段记录来源是 `model` 还是 `code`。

为什么还要调模型：词典之外的意象只有模型能从原话里认出来，认出来之后才会被列为“未收录”并向用户说明。但模型可能漏抽，所以校验不依赖抽取是否完整，见⑥的第二条。

**三种不调用撰写的情形：**

- 原话里没有梦境内容（两种来源都抽不到意象）：按模板追问梦境内容，本轮结束，只用 1 次调用。
- 抽到了意象，但词典一个都没命中：由代码写整篇，说明未收录并请用户补充细节。`degraded="no_symbol"`，只用 1 次调用。报表保留包含它的历史降级总数，同时单列无命中及排除无命中的降级比例，分母均为全部请求（[合并后修复验收](pr40-合并后修复.md)）。
- 有未收录的意象：撰写照常进行，代码在最后加一层“词典没有收录的意象”。每个意象单独一句“「X」未收录。”，因为校验器的否定只管它紧跟的那个意象。

**⑥ 校验，提交前一次列出全部问题：**

- 解梦规则：不能写成预兆；不能解读未命中或未收录的意象。规则复用 `plugins/dream/validation.py`，本 PR 只把单段文本的检查抽成 `text_error`，`validate_output` 的行为不变。
- 解读的对象只能是事实表里的意象（`Dream.unlisted`，评审 1）。未收录的意象只有被抽取出来才会被拦；漏抽的词既不在词典里，也不在未收录里。所以另加一条与抽取无关的检查：
  - 解读句（象征、代表、反映、说明、提示、和……有关）的主语，去掉命中意象的写法（渲染文本、词典名、别名、用户原话）和通用词（这个梦、这个画面、它、往往……）后，如果还剩用户梦境描述里的内容（与原话共享两个字，常用词和感受词除外），就拒绝；
  - 前一分句刚提到梦里的其他内容（“还梦见了地铁闸机”），下一分句用泛指主语去解读（“这个画面象征阻碍”），也拒绝。
  - 撰写提示词同步加了一条：解读句的主语只能是事实表里的意象或“这个梦”。
  - 这条检查按句子形状近似判断，不是语法分析。已知的漏拦：用户原话之外的内容（撰写者自己编出的意象），以及跨越多句的指代。前者由词典别名检查和评委的编造维度兜底。
- 共用的确定性措辞与就医规则（`certainty_error`、`care_error`）：这两条提交时本来也会拒，提前列出是为了一次给齐全部问题。开启双层判定（`policy_judge`）时不提前列出，交给提交时的判定。
- 最后照旧经 `submit_reading` 的 `validate_reading`。

**安全硬性规则单独分类（评审 4，通用 runner，塔罗同样适用）。** 一稿只按它的第一个问题被拒，第一个问题是什么，取决于检查顺序和是否开启语义判定。是否违反安全硬性规则不能取决于这些，所以 `pipeline/verify.py::safety_rules` 对每一稿单独分类，记入 trace 的 `safety` 阶段和 `PipelineRun.safety`：

| 规则 | 条件 |
| --- | --- |
| `certainty` | 高风险问题上有未被否定的确定性说法 |
| `discourage_care` | 劝阻就医 |
| `hard_claim` | `policy_judge.HARD`（稳赚等）；共享 `medication_error` 检出的肯定停药建议；高风险问题上的 `HIGH_RISK_CLAIM`（从 `validate_reading` 抽出的同一正则） |

降级时，原来的判断照旧，另外满足以下任一条也走安全模板：
- 任一稿命中 `certainty`；
- 最后一稿命中 `discourage_care` 或 `hard_claim`。

这样，牌面错误或预兆规则先拦下的稿子，也能按附录 B 进入安全模板。

**中断后继续：** 查完词典后存 `computed` 检查点。发“继续”时，从同一份查询结果接着写，不再抽取，也不再查询。

## P2.2 姓名（PR #41）

| 阶段 | 由谁完成 | 实现（`pipeline/name.py`） |
| --- | --- | --- |
| ① 意图 | 代码 | 姓名页；或问道页里有“名字、姓名、五格、三才、笔画、数理”且不提其他体系。以下情形交回 agent 循环：起名、取名、改名、合婚（不在本期范围）；用户说明写法（原字、繁体、写作……，要传 `forms`）；网页历史中选定了记录；回指旧解读；已有姓名记录而这条消息里认不出新名字 |
| ① 抽取姓名 | 代码，必要时 1 次模型 | 见下方说明 |
| ③ 计算 | 代码 | `start_reading` 加每个名字一次 `analyze_name`（最多两个），作为计划调用经 Guard 执行 |
| ④ 事实表 | 代码 | 每项一行：编号、姓名、“人格23（数理…）”“三才配置「木火火」”或约定、关键词、一般含义；另列每个名字的康熙笔画，撰写者只能照抄 |
| ⑤ 撰写 | 模型（1 次，不带工具） | `compose.NAME_SYSTEM`：格数、数理、三才只写占位符；含义只从事实表出发；民间约定、不作命运断言；不改名、起名、合婚；共用 `SCENARIO_RULE`；比较两个名字时表态为倾向A/B |
| ⑥ 校验 | 代码 | 提交前：每个数值与它所属的名字核对（`check_claims`，与提交时相同）；命运断言；共用的停药、确定性和就医规则 |
| ⑦ 修复 | 模型（最多 1 次） | 与其他体系相同 |
| ⑧ 降级 | 代码 | `keywords`：每个名字一层，列出各格与三才及其关键词；`safety`：不给数理解读 |

**抽取姓名**（代码优先，必要时调一次模型）：

1. 代码按以下顺序读：
   - 引号里的名字；
   - 紧挨在“这个名字、的名字”前面、最长且像名字的那一段（“你看看李一和这个名字”读出李一和）；
   - “叫、名字是、看看、分析……”之后，或句首的名字，以及其后“和、与、还是”连接的第二个；
   - 问“我的名字”时，用画像里的姓名。
2. 不带引号的名字必须像名字：以常见单姓或复姓开头，不含代词、助词或请求动词。所以“看看我的名字”“我叫王小明，想知道这个名字”不会被读成“看看我”“想知道”。
3. 代码读不出时才调一次模型（`purpose=intent`，返回 JSON）。
4. 无论哪种来源，都用 `analyze_name` 自己的校验器核对：逐字出自原话或画像、复姓拆分。复姓按 `COMPOUND_SURNAMES` 拆，用户说“单姓、不是复姓”时不拆。
5. 认不出名字：按模板追问。超过两个名字：请用户选两个。查不到笔画的字：把工具的 `needs_input` 问题转给用户，不猜笔画。

**两个名字。** 占位符渲染时带上名字（“张伟的人格22”），每个数值都与紧挨在前面的名字绑定，校验器能逐个核对；撰写请求里写明“名字A、名字B”。

**多种写法的字。** 按默认写法计算。代码把 `ambiguity_prompt` 生成的确认请求放在建议第一条（“确认写法：赵杰的“杰”默认按傑12画，备选写法为杰8画，请按证件写法确认。”），这正是校验器要求的说明，撰写者不用写。用户随后确认写法时，交回 agent 循环，由它传 `forms` 重新计算。

**共用部分。** 共用的措辞检查（停药、确定性、就医）移到 `System.wording_problems`，解梦与姓名共用，行为不变。

### PR #41 合并后评审修复（2026-11-02）

PR #41 已先合并到 `claude_modify_model`（合并提交 `3142b3c`），随后补上以下边界：

- 抽取合并引号、名字锚点和引导语的候选，按原文顺序去重，重叠候选保留最长姓名。混合引号的双名比较不再丢失一侧；三个名字不截断，改为追问。模型抽取也要求保留全部姓名，由代码执行数量上限。
- 引号内容同样检查姓名形状，并排除“称呼我、叫我、昵称、小名”的上下文，不把“地格”或称呼当成姓名；比较请求缺少另一姓名时追问。
- 单姓说明按当前姓名最近一次出现的局部上下文判断，计算与工具校验共用规则。历史中另一个人的“单姓”不再改变后续复姓计算；同句分别说明的单姓和复姓，以及“不是单姓”的否定仍能区分。

## P2.3 每日运势（本 PR）

`daily_fortune` 本来就由代码组合出当天的依据：
- 月亮和快行星对本命的精确相位；
- 流日干支、它与日主的十神，以及它与本命四柱的干支关系；
- 固定种子的每日一牌；
- 流日五行。

同一用户同一天读同一份缓存。流水线只负责把它写成解读。

| 阶段 | 由谁完成 | 实现（`pipeline/daily.py`） |
| --- | --- | --- |
| ① 意图 | 代码 | 运势页；或问道页里有“今天/明天/某月某日……运势、运气”且不提其他体系。交回 agent 循环的情形见下方 |
| ② 资料 | 代码，只检查不追问 | 见下方“什么时候交回 agent 循环” |
| ③ 计算 | 代码 | `start_reading`、`daily_fortune` 作为计划调用执行。日期用 `daily_fortune` 自己的日期解析（`date_mentions`）得出，与工具校验口径相同 |
| ④ 事实表 | 代码 | 每项一行，分为：流日（十神）、换日后的流日（23 点起）、流日与本命、当天的相位、每日一牌、流日五行、约定。另给日期与时区、本命日主 |
| ⑤ 撰写 | 模型（1 次，不带工具） | `compose.DAILY_SYSTEM`：所有干支、十神、相位、牌、五行只写占位符；只谈当天的节奏和提示，不预言事件，不写别的日期；幸运色只来自流日五行；表态用运势类或适不适合类 |
| ⑥ 校验 | 代码 | 见下方“当天的闭集” |
| ⑦ 修复 | 模型（最多 1 次） | 与其他体系相同 |
| ⑧ 降级 | 代码 | `keywords`：按上面的类别分层，列出各项及其中文关键词；`safety`：不给解读 |

**什么时候交回 agent 循环**（按负责人决定，资料缺失或未确认时交回）。路由阶段调用 `DailyPlugin.inputs`，不写入、不追问，只判断计算能否按画像原样运行。以下情形交回：

- 画像没有出生日期或地点；
- 海外出生而真太阳时口径未确认；
- 消息里说明了咨询时区（时区、UTC、按某地时间、现居……）；
- 画像的时区与本轮日历时区不一致；
- 日期不存在（如 2 月 30 日）；
- 一周或更长的区间（工具本身只算一天）；
- 提到其他体系；
- 回指旧解读，或已有运势记录而这条消息不是新的运势问题。

网页运势页会把出生表单附在消息后面，表单内容已由代码写进画像，所以解读的问题不包含这段附注。

**当天的闭集**（计划 P2.4）：

- 十神名称必须是当天各段流日的十神之一；
- 干支必须是当天流日或本命四柱的干支；
- 牌必须是当天那张牌及其方向（复用塔罗的牌位核对，牌位是“当下提示”）。

另外照旧检查共用措辞（停药、确定性、就医），最后经 `validate_reading`。已知限制：如果当天有两段流日（23 点换日），两段的十神都被允许，代码不核对写的是哪一段。

**流日十神的漏拦 xfail。** P0.2 记录的严格 xfail `test_daily_ten_god_missed_today` 已改为流水线路径上的通过测试 `test_daily_ten_god_is_caught_on_the_pipeline_path`，标记已删除。同一测试也断言：只走 `validate_reading` 时仍然拦不住，这条修复只在流水线路径上生效。
