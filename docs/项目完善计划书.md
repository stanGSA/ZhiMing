# 知命项目完善计划书

2026-10-20 · 基线：main `3f70de8`（PR #12 合并后）· 配套原计划：[占卜Agent项目计划书](占卜Agent项目计划书.md)

## 一、背景与目标

项目第 1–6 周的工程部分已经完成：手写 harness、guard 硬约束、确定性排盘与抽牌、带版本快照的知识库、嵌套 trace，六个占术插件全部接入，单、多 Agent 两种模式都能运行。但对照原计划书，还有四类缺口：

1. 第 7 周的评估与对照实验没有做，多项关口没有数字。
2. 知识库 1171 条全部是草稿，人工审核率 0%；感情、财运两个主题在占星和八字里没有方向。
3. 已测的真实模型关口有三项未过；默认模型换成 DeepSeek 后没有做过真实回归。
4. 网页版只覆盖一半体系，身份、限流、流式输出等产品能力不足。

本计划的目标：

- 默认配置（DeepSeek）经过真实模型验证，结果入档。
- 知识库的可信度有可复核的依据。人工审核由**模型交叉审核**替代，替代方式见第四节。
- 原计划书的评估指标全部给出第一版数字，对照实验出图。
- 网页版覆盖六个体系，可以安全地给他人使用。
- 修掉已发现的正确性缺陷，降低维护成本。

范围：沿用原计划书的非目标（吠陀占星、紫微斗数、专家自由辩论、付费账号系统、语音）。梅花易数、起名、合婚/合盘仍属第二阶段，放在本计划最后。

## 四、知识库与评估：用模型交叉审核替代人工审核

项目负责人无法完成逐条人工审核，改由另一个大模型审查。这一替代**有两个前提**：

1. **模型审核的结论不能记成“人工审核”。** `reviewed: true` 继续只表示人工审核，模型审核单独记录状态，不得写入 `reviewed`。README、验收报告和对用户的置信度说明都如实写“经模型交叉审核，未经人工审核”。这延续项目一贯的做法：`reviewed` 不冒充人工审核。
2. **审核标准要按“模型交叉审核”重新定义。** 原关口“人工审核率 ≥ 95%”不能直接套用到模型审核上，改为一组可复核的指标：双模型交叉审核通过率、埋错检出率、重跑一致率和模型间一致率（见 4.8）。只有这组指标全部达标，才算知识库关口通过。

### 4.1 模型能审什么，不能审什么

| 能比较可靠地审 | 不能审或不可靠，另行处理 |
| --- | --- |
| 释义核心含义是否符合主流传统，如塔罗正逆位有没有写反、十神含义有没有偏 | 冷门流派的细节：模型会把流行但不准确的说法当成正确。在条目 `source` 里注明流派，不宣称权威 |
| `theme_map` 的正负方向是否和释义文字一致 | 权重的具体数值：本来就是主观约定。只审方向和相对大小，数值由规则文件统一管理 |
| 有没有“必然”“注定”等宿命化说法，有没有医疗、投资、法律方面的确定性断言 | 是否抄袭古籍整理版或现代书籍：模型最多只能标“疑似”，疑似条目改写后重审 |
| 术语附带的白话解释是否准确；解梦同义词会不会误命中 | 危机热线号码：只从官方渠道核实，记录来源网址和核实日期，不依赖模型记忆 |

### 4.2 审核状态与置信度

- 条目新增 `review_status` 三态：`draft`（草稿）、`model_reviewed`（模型交叉审核通过）、`human_reviewed`（人工审核）。保留 `reviewed: bool` 且只表示人工审核；`knowledge.build` 校验两者一致（`reviewed == (review_status == "human_reviewed")`）。
- 条目新增 `model_review` 记录：两个审核模型的厂商与模型名、日期、各自结论、发现的问题、审核报告路径。
- `Signal` 由 `reviewed: bool` 扩展为审核级别，合并时取各组成部分中的最低级别（与现在“全部审核才算审核”的规则一致）。
- 置信度映射（修改 `common/output_policy.py` 的 `mark_unreviewed`）：

| 本次用到的信号中最低审核级别 | 置信度上限 | confidence.reason 的说明 |
| --- | --- | --- |
| `draft` | low | 释义未经审核 |
| `model_reviewed` | medium | 释义经模型交叉审核，未经人工审核 |
| `human_reviewed` | 不设上限 | 无需说明 |

- 条目状态变更会改变知识库版本号；旧 reading 继续引用旧版本快照，不受影响。

### 4.3 审核模型的选择

- 用**两个不同厂商**的模型各自独立审核，且都不能和运行时模型（DeepSeek）同一厂商。同一家模型审自己写的东西有明显的自我偏好。
- 起草条目的模型目前没有记录。今后起草时记录起草模型，审核模型须与起草模型不同厂商。
- 两个审核模型互相看不到对方的结论（盲审），也不知道哪些条目是埋入的错误（4.6）。
- 需要两家都判“通过”才算 `model_reviewed`。任一方判“需修改”或“拒绝”，条目保持 `draft`，问题进入修改队列；修改后两家重新审核。

### 4.4 审核流程

1. **代码检查先行**：数值范围、正逆位倾向是否相反、禁用词（必然、注定、一定会等）、id/key/同义词唯一性，先在 `knowledge/build.py` 里检查。代码能判断的问题不交给模型。
2. **分批审核**：按体系和条目类型分批，每次调用约 10 条，输出固定 JSON 结构。脚本支持断点续跑，并缓存已完成的批次。
3. **合并结论**：按 4.3 的规则合并两家结论，生成修改队列。
4. **修改与复审**：修改由另一次模型调用（或人工）完成，修改后必须两家重新审核，不能由审核模型直接改写后自动通过。
5. **存档**：每批的输入摘要、两家原始输出、合并结论存入 `docs/verification/kb-model-review/`，源文件的 SHA256 与知识库版本一并记录。
6. **构建**：`knowledge.build` 输出覆盖率报告时，按体系分别统计 `draft` / `model_reviewed` / `human_reviewed` 三种比例。

### 4.5 审核维度

每条条目给出 `pass` / `revise` / `reject` 之一，并逐项说明理由。

| 范围 | 审核维度 |
| --- | --- |
| 通用 | 核心含义符合主流传统；释义文字与 `theme_map` 方向一致；没有宿命化或确定性断言；没有医疗、投资、法律的具体结论；术语附带的白话准确；不疑似原文抄录；与同类条目不重复、不矛盾 |
| 塔罗 | 正位、逆位含义区分清楚，倾向方向关系合理；牌位条目与牌阵定义一致 |
| 占星 | 行星、星座、宫位、相位的基本性质；行星落座、落宫的主题方向（配合 B1 补齐） |
| 八字 | 天干地支、十神、五行生克、冲合刑害的描述准确，不把冲合说成灾祸；十神对感情、财运的方向（配合 B1） |
| 姓名 | 81 数理与三才的吉凶写成民间约定，不作命运断言 |
| 解梦 | 同义词不会误命中其他意象；不写预兆；死亡、疾病、怀孕等敏感意象措辞平和 |

### 4.6 可信度校准：埋错检测

原计划书用人工抽查 20 条来校准评审可信度。没有人工时，用以下三种方法替代：

- **埋错检出率**：每批混入约 10% 故意改坏的条目，审核模型不知道哪些被改过。改法包括：反转 `theme_map` 正负号；交换正位与逆位文字；插入“必然破财”等宿命化句子；插入医疗诊断式说法；把释义换成另一个条目的文字；给解梦条目加一个会误命中的同义词；把十神或五行写错。统计每个审核模型和两家合并后的检出率。
- **重跑一致率**：同一模型对同一批条目审两次，结论一致的比例。
- **模型间一致率**：两家对未改动条目的结论一致程度（Cohen's kappa）。

### 4.7 同样适用的场景

- **主题权重补齐（B1）**：由模型 A 提出 relationship、finance 的方向与数值，模型 B 复审，代码检查方向与文字一致后再入库。提出者和复审者不能是同一个模型。
- **评估数据集（C6）**：六份草稿数据集的标注由两家模型交叉审核，数据集元数据里记录审核方式为“模型交叉审核”，不写“人工审核”。
- **真实测试评分（C5）**：rubric 评分模型改为与被测模型不同厂商；`evals/judges/` 存放固定 rubric。

### 4.8 新的验收口径

替代原关口“条目审核率 ≥ 95%（人工）”：

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 双模型交叉审核通过率 | 每个体系 ≥ 95% | 两家都判通过的条目占比 |
| 埋错检出率 | 两家合并 ≥ 90%，单个模型 ≥ 80% | 达不到说明审核不可信，先改 rubric 或换模型再审 |
| 重跑一致率 | ≥ 90% | 同一模型两次审核的结论一致比例 |
| 模型间一致率 | kappa ≥ 0.6（首轮后再调） | 低于目标时检查 rubric 是否有歧义 |
| 未通过条目 | 不得标为 `model_reviewed` | 保持草稿，解读继续标低置信度 |
| 人工审核率 | 如实报告（目前 0%） | 不因模型审核而改变 |

### 4.9 成本与改动范围

- **成本**：1171 条 × 2 家模型，每次调用约 10 条，粗估一两百万 token；另加约 10% 的埋错条目和一次重跑。实际取决于提示词长度和所选模型。
- **代码改动**：`knowledge/schema.py`、`knowledge/build.py`、`plugins/base.py`（Signal）、`signals/merge.py`、`common/output_policy.py`、各插件传递审核状态的位置，新增 `scripts/model_review_kb.py`、`evals/judges/`，约十几个文件。
- **试点**：先审塔罗 163 条，验证 4.8 的指标和流程，再推广到其余体系。

## 五、分阶段实施计划

### 5.1 执行规则

1. **按阶段执行，不按 A~G 的顺序执行。** A~G 是按领域的问题分类，用于在提交、PR 和验收报告中引用编号；阶段 0~5 是执行顺序，每个阶段从多个分组中取任务。问题之间有依赖，按分类顺序做会返工：
   - 阶段 2 的评估要在阶段 0 的 DeepSeek 复测（C1）和阶段 1 的知识库修改（B1、B2）之后进行，否则知识库一改，评估就要重跑；
   - 阶段 4 的重构（F1、F2）要在阶段 2 有了评估基线之后进行，才能判断重构有没有让回答变差；
   - 第二阶段功能（G）要等插件自动注册（F3）完成，否则每加一个体系都要改十几处。
2. **同一阶段内先 P0，再 P1、P2。**
3. **网页可以并行。** 阶段 3 与阶段 1、2 基本互不依赖，人手足够时可以同时推进。并行时注意两点：
   - 阶段 3 只改网页接口和前端，不改变 runtime 的回答行为（提示词、工具结果、校验规则、知识库），避免影响阶段 2 的评估数字；
   - 网页上的置信度文案要等阶段 1 的审核状态（4.2）确定后再定稿。
4. **小任务不用等阶段。** 同时满足以下三个条件的任务可以随时插入执行，不必等到所属阶段：
   - 改动小，半天内能完成，并有测试；
   - 不依赖其他阶段的结果；
   - 不改变模型看到的提示词、工具结果或校验规则，因此不影响评估基线。

   当前符合条件的有：F6（LICENSE 与 NOTICE）、A3（排盘改到线程中执行），以及 F8 中的 `fetch_data` 失败后继续下载、缺数据时测试跳过、测试临时目录清理、Anthropic `cache_control`。阶段 2 的评估批次运行期间，凡是会改变回答行为的改动，都等该批次跑完再合并。

## 六、风险与应对

| 风险 | 应对 |
| --- | --- |
| 审核模型和起草模型有相同的训练偏差，会一起“确认”流行但不准确的说法 | 两家不同厂商盲审、埋错校准、对外如实写“未经人工审核”、在 `source` 中注明流派 |
| 审核成本或接口限流超出预期 | 分批、断点续跑、缓存已完成批次；先用塔罗试点估算实际成本 |
| DeepSeek 实测不达标 | 保留切换 provider 的能力，与 `gpt-6.1-sol` 基线对照后再决定默认模型 |
| 收敛正则时引入回归 | 每次只改一类规则，配合现有测试和变异检查 |
| 开源协议合规 | 按 AGPL-3.0 公开源码；分享模式页面注明源码地址 |
| 回复篇幅持续膨胀，成本和延迟上升 | 在评估报告中长期跟踪字数、token 与耗时 |

## 七、需要项目负责人决定的事项

1. **审核模型用哪两家**：需要两家与 DeepSeek 不同厂商的 API key。代码已支持 Anthropic 和其他兼容 OpenAI 接口的服务。
2. **模型交叉审核后的置信度上限**：建议为 medium（4.2），也可以保持 low。
3. **默认面向地区**：决定危机热线配置（E1）。
4. **网页是否需要账号和跨设备同步**：决定 D3 采用“浏览器身份持久化”还是正式账号。
5. **开源协议**：建议 AGPL-3.0（F6）。
6. **喜用神的处理方式**（B4）：在确定性层按某一流派实现，还是禁止模型推断喜用倾向。
7. **第二阶段做哪些功能**及先后顺序。
