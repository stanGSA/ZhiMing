# 网页界面改版

日期：2026-10-23。依据画布样稿把原先“侧栏 + 卡片 + 主题换色”的单页界面，改为一个入口页、一个问道首页和六个功能页。每一页按其主题单独设计，按钮形制也随主题变化；功能、接口和校验规则沿用原有实现。

| `/ask` | 问道 | 千里江山青绿：绢色底、石青石绿山峦、朱砂印；六术目录 | 石青方印「问」 |

## 接口变化

- `ChatInput.system` 增加 `name`、`dream`、`daily`，消息末尾注明“本次希望使用姓名五格／解梦／每日运势来解读”。只有问道、八字、星盘、运势会附带出生资料；塔罗、解梦、姓名不发送。
- 离线演示只会抽塔罗，因此解梦、姓名、运势在离线演示中返回 `demo_unsupported` 提示，不再用牌面代答。
- `PUT /api/birth`：保存生辰档案，各页共用；生辰改变时清除旧命盘。
- `POST /api/name`：按 `plugins.name.wuge.analyze` 直接计算康熙笔画、五格、三才，不调用模型；有多种写法的字返回备选，由用户选择后重算。
- `POST /api/almanac`：按 lunar-python 给出某日的年月日干支、农历、节气与物候、日元素及知识库中的配色说明、本周流日；填写了出生日期与地点时，按日主推算各日十神。流日取当地正午所在日柱。
- 会话列表 `history` 改由 `Store.reading_history` 提供，额外带 `systems_used` 与 `created_at`，供足迹与梦境日记显示；交给模型的 `recent_readings` 不变。
- 会话仍有效时访问 `/` 会 303 跳转到 `/ask`；入口页设为 `Cache-Control: no-store`，避免浏览器缓存旧的入口。

## 范围与限制

- 账号登录与跨设备同步尚未实现。入口页的“账号登录”页签明确标注“筹备中”，输入框不可用；可用的是访客入内与离线演示。
- 每日一牌与行运相位仍来自完整的运势解读（需真实模型），在详解后显示；页面直接计算的只有历法部分。
- 本次未在真实模型下做端到端解读，只验证了离线路径和接口。

## 验证

- `tests/test_web.py` 新增 6 项：各页地址与入口跳转、不含内联样式；新体系的提示语与出生资料范围；离线演示不以牌面回答解梦、姓名、运势；`/api/name` 对“陈知远”得出天格 17、人格 24、地格 25、外格 18、总格 41、三才金火土，并拒绝非汉字与无关写法；`/api/almanac` 对 2026-10-22 得出丙午年、戊戌月、己巳日、九月十三、次日霜降，按 1994-03-18 08:30 杭州西湖区的日主癸水得出当日七杀及整周十神；生辰保存与命盘失效。
- 在本机用 Chromium 检查 8 个页面：1440 与 390 像素宽度均无横向溢出、无脚本错误。离线演示下走通：八字排盘、星盘绘制、姓名推演与写法选择、三张牌抽牌与解读、问道首页解读与近来所问、足迹回看、切换运行模式、清除记录、解梦与运势的离线提示。
- Ruff 检查与格式检查通过。完整测试中，`test_doctor_week1_required_checks` 只因本机网络策略无法下载 JPL `de440s.bsp` 而失败，与界面改动无关；CI 会下载该文件。

## 第二轮：对话窗与塔罗翻牌

针对“与模型对话的入口太隐蔽”与“塔罗缺少交互感”，只改前端，接口与校验不变。

- **对话窗**：问道、八字、星盘、塔罗、姓名、运势六页统一为带边框的对话窗：页眉（印章、标题、连接状态）、左右分列的问答气泡、底部常驻输入框与发送键，输入框随文字增高。对话窗与解读面板并排，放在命盘、星图或日历正下方；宽屏时对话窗吸附在视口内，滚动阅读长解读时仍可发问。配色、边框与圆角沿用各页主题，由 `--dialog-*`、`--bubble-*` 变量控制。解梦页的记梦信笺未改。
- **浮动入口**：对话窗不在视口内时，右下角出现「问 · 对话」按钮，点按回到对话窗并聚焦输入框；塔罗页尚未抽牌时回到“所问”。
- **问道**：去掉原先压在山峦上的「所问」长卷与「问」字大印，提问改在“问答”区的对话窗内完成；六术、近来所问、生辰档案保留。
- **生辰折叠**：八字、星盘、运势的生辰表单移到标题下方，折叠为一行摘要（如“公历 1994-03-18 08:30 · 中国 · 浙江省 · 杭州市 · 西湖区 · 女”）。未填写时八字、星盘默认展开；排盘或保存后自动收起并滚到命盘。运势页的「填写生辰」与缺资料提示会展开它。
- **塔罗**：步骤条（选牌阵 → 写下所问 → 从牌堆选牌 → 翻牌见意）。点「洗牌抽牌」后，78 张背面朝上的牌收拢再展开成扇形，逐张点选，选中的牌飞入牌位；选满后发问，牌以背面落位，轻触逐张翻开（或「全部翻开」）。全部翻开前，牌意与回答保持模糊。之后的追问在对话窗进行；刷新或回看历史时直接显示牌面。在对话窗或建议问题里先写问题，会填入“所问”并开始选牌。
- **选牌决定牌面**（审核后选定方案 A）：会话种子仍按 `tarot-sha256-v1` 排出整副 78 张的顺序，相当于洗好、背面朝上摊开；用户点中的位置（`picks`，0–77，按牌位顺序）决定抽到哪几张。牌扇下方写明“你点中的位置，就是抽到的那张牌”。
  - 网页：`POST /api/chat` 增加可选的 `picks`，只用于塔罗，须与牌阵张数相符且互不重复，否则返回 422。每次请求都重设，选择不会带到之后的问题。
  - 会话：`Session.pending_picks` 由 `start_reading` 写入本次记录的状态并清空，只用一次；塔罗专家子会话继承同一记录的 `picks`。抽牌工具拒绝与所选张数不符的牌阵。
  - 结果：抽牌结果与入库的 `tarot_json` 带 `picks`；`draw_tarot(spread, question, seed, picks)` 可完全重算，`scripts/gate_evidence.py` 的回放校验已传入 `picks`。不带 `picks` 时结果与原来逐字节相同，命令行、评测与历史记录不受影响。

验证：新增测试覆盖 `picks` 的取牌、非法输入、单代理与塔罗专家两条路径、只用一次、牌阵不符被拒、网页接口校验与入库重算。浏览器中点选第 61、9、35 位后，入库记录的 `picks` 与之相同，按种子与 `picks` 重算得到同样三张牌，且与不选时的最上面三张不同。在本机用 Chromium 检查 390、768、1100、1440 像素宽度七个页面均无横向溢出、无脚本错误；离线演示下走通问道发问、八字排盘与发问、星盘绘制与发问、塔罗单张与三张的选牌—翻牌—追问、刷新后牌面保持、选牌中途开启新对话、运势发问。本环境的网络策略拦截了 Unihan、geonamescache 与 JPL `de440s.bsp` 数据下载，姓名推演只检查了空状态。完整测试 786 项通过；91 项因缺上述数据文件失败或报错，与未改动代码上失败的 91 项完全相同。
