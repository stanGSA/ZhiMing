## 1. 根因回顾

问答失败的表现各不相同，根因是同一个设计：

> 事实由代码算出，却要模型抄写进自由文本；另一套独立维护、以正则为主的校验器再逐项核对；不一致就退回让模型自己改，而一次问答只有 12 步。

它由三个结构性缺陷组成：

| 缺陷 | 表现 | P1 证据（Final-single，flash，60 题） |
| --- | --- | --- |
| D1 模型复述事实 | 干支、牌名、正逆位、`ref_id` 抄错被退回；长 JSON 引号转义出错 | 事实与计算不符 33 次；参数不符合 schema 8 次 |
| D2 规则写两份 | 提示词约 2.1 万字节，校验约 1500 行，两边对不上：正确答案被拒，提示词允许的事代码禁止 | 画像写入越界 74 次（27 题）；`cc48c57` 误拒正确的"流日壬戌" |
| D3 流程交给模型 | 模型自己选工具、自己追问、自己猜 key；走错一步就消耗一步 | 资料未确认就计算 48 次；10 题耗尽步数或预算；`37fb626` 连续四轮猜 key |

整体指标（`docs/verification/p1/codego-v4/comparison.md`）：

| 版本 | 任务完成 | 已提交回答 | 无工具错误 | 已提交回答的质量通过率 | 错误/题 | 调用/题 | P50/P95 秒 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Final-single | 37/60 | 25/60 | 14/60 | 13/25 | 2.97 | 8.13 | 92.2/280.3 |
| Final-multi | 33/60 | 22/60 | 19/60 | 11/22 | 2.45 | 9.22 | 106.6/231.9 |
| Compare-single（多体系 12×3） | 11/36 | 12/36 | 2/36 | 8/12 | 5.14 | 9.86 | 117.4/284.7 |
| Compare-multi-lite | 6/36 | 8/36 | 6/36 | 4/8 | 5.25 | 11.28 | 148.6/254.3 |

**multi-lite 给的教训。** `agents/lite.py` 已经把专家的计算改成代码规划（D3 的一部分），但结果没有变好（6/36 对比 11/36）。原因有两点：专家仍要用 `submit_report` 复述事实（D1 没动），编排者仍是 agent 循环（D3 只改了一半）。所以这次整改必须**在同一条路径上同时消除三个缺陷**，只改一处不会见效。

## 2. 目标与非目标

### 目标

1. 问答主路径改为"代码驱动流水线"：模型只做两件事，理解问题和写解读。
2. 模型不再亲手书写可核验的事实。事实由代码渲染，抄错这件事不可能发生。
3. 规则只保留一份来源，同时生成提示词片段、schema 约束和校验分发。
4. 失败不再表现为"达到步数上限"：最多修复一次，修不好就降级输出。
5. 流水线的每个阶段都落库，刷新页面或进程重启后能从上次完成的阶段继续。

### 非目标（本次不改）

- 计算器、星历、知识库内容和审核流程（`plugins/*/calculator.py`、`knowledge/`）
- 危机识别和安全回复（`common/safety.py`、`Runtime.safety_response`），流水线在它之后执行
- MCP server 和 `plugins/direct.py` 的对外接口
- 已保存解读的格式：继续使用 `common.schemas.Reading`，存储、`render_reading`、网页面板都不用改
- 更换运行模型

## 3. 目标架构

### 3.1 一次问答的流程

```
用户消息
  │
  ├─ 危机检查（现有 Runtime.safety_response，不变）
  │
  ▼
① 意图解析  intent            代码抽取优先；只有代码判断不了的部分调用 1 次模型（结构化 JSON），结果经代码校验
  ▼
② 资料检查  requirements      纯代码：按"资料需求表"检查；缺资料或需确认时按模板追问并结束本轮，下一轮从这里继续
  ▼
③ 计算      compute           纯代码：按意图生成计划调用，经 Guard 执行（来源校验、缓存、trace 不变）；
                              计算器抛出 NeedsInput 时转为追问
  ▼
④ 事实表    factsheet         纯代码：从本次计算汇总可引用事实，含编号、短标签、白话释义、时间属性
  ▼
⑤ 撰写      compose           1 次模型调用，无工具：只看问题、意图和事实表，用 {{R3}} 引用事实
  ▼
⑥ 渲染校验  render + verify   代码：解析为 Reading → 展开占位符 → 闭集比对 → 现有 validate_reading 兜底
  │                            ├─ 可自动修复 → 代码修正，记录 trace
  │                            ├─ 需要模型修 → ⑦
  │                            └─ 通过 → 保存并返回
  ▼
⑦ 定向修复  repair            最多 1 次模型调用，只重写出错的段落
  ▼
⑧ 降级      degrade           仍不过：删掉出错的段落，或输出代码模板生成的"事实加释义"摘要，标注 partial
```

每题的模型调用上限：意图解析 ≤ 1、撰写 1、修复 ≤ 1，**合计不超过 3 次**。不再有"步数"概念，墙钟上限沿用 `limits.request_timeout_s`。

### 3.3 撰写的输出约定（D1 的核心）

**模型只写这些字段：** `verdict`、`summary`、`sections[].title`、`sections[].body`、`sections[].refs`、`advice`、`closing`；多体系时再加每条张力的 `how_to_read`。

**以下字段由代码填写：**

| 字段 | 来源 |
| --- | --- |
| `question_type` | 意图 |
| `systems_used` | 本次实际产生信号的体系 |
| `evidence` | 正文用到的引用编号，附录文本由 `calculation_evidence_texts` 渲染 |
| `tensions[].theme/sides` | `merge_signals` 的结果 |
| `confidence` | 按知识库审核等级生成模板文本 |
| `safety` | `HIGH_RISK` 命中时使用分类模板 |
| `followups` | 按意图生成的模板 |

**输出格式：普通文本加轻量标记，不放进工具调用的 JSON。** 示例：

```
【表态】suitable
【摘要】十一月整体适合启动求职，主要助力来自{{R4}}；前提是先把简历和作品集准备好。
【分层】节奏偏快，适合主动出击
{{R4}}落在事业相关的位置，往往意味着……
【引用】R4 R7
【分层】……
【建议】
- 先投核心岗位：……
【收尾】……
```

- 代码把它解析成 `Reading`；标记缺失或顺序错乱都算"格式错误"，进入一次修复。
- `{{R3}}` 由代码展开为短标签。各插件新增 `fact_label(fact, form)`，`form` 有两种：
  - `plain`：用于摘要、标题、建议，例如"流年（丙午）"
  - `term`：用于正文，例如"流年丙午与日柱壬子相冲"
- `【引用】` 只能写本次事实表里的编号，代码按集合校验；正文里的 `{{Rn}}` 自动并入引用。

**闭集比对。** 正文中直接出现的事实词与事实表比对：

| 闭集 | 来源 |
| --- | --- |
| 牌名与正逆位 | 78 张牌，`DECK` |
| 干支 | 60 甲子 |
| 星座、行星、相位 | 名称表 |

| 比对结果 | 处理 |
| --- | --- |
| 与本次事实一致 | 通过 |
| 能唯一对应到某个事实 | 自动改写成占位符展开后的文本，记录 `auto_fixed` |
| 与本次事实矛盾或不存在 | 真错误，进入修复 |
| 一般牌义的说明句（如"逆位一般表示……"） | 沿用 `orientation_error` 现有的定义句判断，迁移期保留 |

### 3.4 意图（Intent）的定义

```
systems:        list[astro|bazi|tarot|name|dream|daily]   专用页面直接给定；问道页才需要判断
question_type:  timing|decision|trait|tarot|daily|name|dream|dayun_overview|followup|unsupported
timeframe:      {start, end, tz?} | None                  优先取 question_range 的代码结果
spread:         single|three_card|decision|None           优先取用户选牌和关键词
entities:       names[]（必须逐字出现在原话中）、dream_phrases[]、options{A,B}
followup_of:    reading_id | None
confidence:     high|low                                  low 时按模板追问，不硬猜
```

- **代码优先**：时间范围、牌阵、性别、真太阳时选择、大运概览、追问判断，现有函数都能处理。
- **模型补全**：问道页的体系选择、问题类型、梦境短语、姓名抽取、A/B 选项。沿用 `app.py` 安全分类器的做法：不传工具，要求返回 JSON 文本，`json.loads` 后用 pydantic 校验。
- **冲突处理**：模型给出的时间范围与代码抽取的不一致时，以代码为准；代码没抽到而模型给了，就按模板追问确认。

## 5. 验收指标

基线为 Final-single（flash，60 题，rubric v2，评委 pro）。这是历史基线，比当前 main 旧（见附录 A）。各阶段的对照以同批次、当前 main 上的 single 为准，并记录源码指纹。目标值在 P1 试点后可以校准一次，校准要写明理由，之后不再改。

"无工具错误"沿用 P1 的 `first_try_clean`，不要求任务完成（Final-single 14/60，其中包含任务失败的运行），只作历史对照。"任务完成且一次做对"另行定义如下表。

| 指标 | 基线 | 目标 | 保证方式 |
| --- | ---: | ---: | --- |
| 已提交回答 | 25/60 | ≥ 55/60 | 结构（降级输出也算提交，另列 partial 比例） |
| 任务完成且一次做对（流水线：无工具错误、无修复、无降级；旧 agent：任务完成且无工具错误） | 12/60 | ≥ 45/60 | 结构加提示词 |
| 步数或预算导致的失败 | 10 题 | 0 | 结构 |
| 每题模型调用 | 8.13 | ≤ 3 | 结构 |
| 每题输入 token | 约 66,972 | ≤ 20,000 | 事实表紧凑，无多轮历史 |
| P95 耗时 | 280.3 秒 | ≤ 90 秒 | 调用次数少 |
| 事实错误（`no_fabricated_facts` 失败次数） | 8 | 0 | 渲染 |
| `time_consistent` 失败次数 | 21 | ≤ 5 | 时间范围由代码决定 |
| 已提交回答的质量通过率 | 13/25 | ≥ 基线，争取 ≥ 70% | 撰写提示词（只能实测，不能由结构保证） |
| partial（降级）比例 | — | ≤ 10% | 监控项 |
| 回退到 agent 的比例 | — | ≤ 10% | 监控项；偏高说明意图类型需要扩充 |
| 留出集 | 16/17 | ≥ 16/17 | — |

**评测执行**

- 真实模型批次由负责人在本机（`D:\知命`）用现有的 `scripts.p1_campaign` 串行执行。原始 trace 保存在忽略目录，只把摘要提交入库。本仓库的云端环境没有模型密钥，不跑付费批次。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 意图解析成为单点 | 分类错了，整题就错 | 代码优先、模型补全；低置信度时追问；把 80 题轨迹集（`evals/cases/trajectory.yaml`）改成意图准确率评测，CI 中离线运行 |
| 规划外的问题 | 流水线答不了 | 走受限的 agent 回退路径并统计比例；比例偏高就补问题类型 |
| 占位符让文字生硬 | 可读性下降 | `fact_label` 分 plain 和 term 两种形式；评测中单独看 `direct_answer`、`supported_conclusion` |
| flash 不遵守标记格式 | 解析失败 | 格式错误算可修复错误，一次修复后仍失败就降级；P1 试点时统计格式错误率，必要时简化标记 |
| 旧模式和新模式并存期间维护成本高 | 修 bug 要改两处 | 旧模式冻结，只修安全问题；P5 决定后删除 |
| 结构变化导致与历史评测不可比 | 难以归因 | 评测脚本、数据集、评委、rubric 版本固定；每个批次记录源码哈希，沿用现有 `*-source-hashes.json` 机制 |
| main 在实施期间继续前进 | 合并冲突 | `claude_modify_model` 定期合并或变基到 main；流水线是新增目录，冲突面主要在 `app.py`、`config.yaml`、`memory/store.py` |
